# 项目解释：RAG-based AI Pre-sales Knowledge Assistant

## 1. 这个项目是什么？

这个项目是一个面向 B2B SaaS 售前场景的 RAG 知识库助手。

它的作用是：当销售、售前工程师或客户成功人员遇到客户问题时，系统可以从已有的产品文档、价格政策、部署说明、安全说明、API 文档、客户案例和异议处理材料中检索相关内容，并生成带来源引用的回答。

简单来说，这不是一个普通聊天机器人，而是一个“基于企业知识库回答问题”的 AI 助手。

---

## 2. 这个项目解决什么业务问题？

在 B2B SaaS 售前场景中，客户经常会问这些问题：

* 产品支持哪些功能？
* 价格和套餐有什么区别？
* 是否支持私有化部署？
* 数据安全和权限控制怎么做？
* 能不能和客户现有系统集成？
* 有没有类似行业的客户案例？
* 如果客户质疑价格太贵，售前应该怎么回答？

如果完全依赖人工查资料，会出现三个问题：

1. 查找资料慢，影响客户响应效率。
2. 不同销售人员回答不一致，影响专业度。
3. 人工回答容易漏掉依据，尤其是价格、安全、部署等敏感问题。

所以这个项目用 RAG 技术，把分散的售前资料整理成一个可检索的知识库，让系统先找依据，再生成回答。

---

## 3. 为什么不用普通 ChatGPT？

普通 ChatGPT 不知道企业内部的最新产品资料、价格政策、部署方案和客户案例。

如果直接问普通 ChatGPT，它可能会出现两个问题：

1. 回答看起来很流畅，但不一定符合公司真实资料。
2. 它可能产生幻觉，编造不存在的产品能力、价格或案例。

RAG 的价值在于：

先从企业知识库中检索相关文档片段，再基于这些片段生成回答。

这样可以让回答更准确、更可追溯，也更适合 B2B 售前这种需要可信依据的场景。

## 4. 项目文件结构说明

当前项目主要分成以下几个部分：

```text
RAG-BASED-AI-PRESALES-KNOWLEDGE-ASSISTANT/
├── knowledge_base/
├── rag_app/
├── outputs/
├── eval/
├── vector_store/
├── docs/
├── README.md
└── requirements.txt
```

### knowledge_base/

这个文件夹是项目的业务知识库，里面存放模拟 B2B SaaS 公司的售前资料。

包括：

* 产品介绍
* FAQ
* 价格和套餐
* 部署指南
* 安全与治理
* API 与集成
* 客户案例
* 异议处理
* 售前邮件模板

这些文档就是 AI 回答问题时的知识来源。

### rag_app/

这个文件夹是 RAG 系统的核心代码。

它负责：

1. 读取知识库文档。
2. 把长文档切成 chunks。
3. 把 chunks 转成 embeddings。
4. 把 embeddings 存入 Chroma 向量数据库。
5. 根据用户问题检索相关 chunks。
6. 基于检索结果生成回答。

### outputs/

这个文件夹保存项目运行后的输出结果。

例如：

* 文档切分结果
* 示例回答
* Chroma 版本的回答结果

它可以证明项目不是停留在代码层面，而是真的能跑出结果。

### eval/

这个文件夹用于存放评估问题集。

它的作用是测试系统面对不同售前问题时，是否能检索到正确来源，并生成合理回答。

### vector_store/

这个文件夹是 Chroma 向量数据库的本地存储位置。

它保存的是文档 chunks 对应的向量索引，用于后续语义检索。

### docs/

这个文件夹用于存放项目说明、面试材料和项目包装文档。

例如：

* 项目解释
* 面试 Pitch
* 项目总结
* 架构说明
* Query Walkthrough

## 5. RAG 工作流程

这个项目的核心流程如下：

```text
Markdown 知识库
↓
读取文档
↓
切分 chunks
↓
生成 embeddings
↓
存入 Chroma 向量数据库
↓
用户提出问题
↓
检索最相关的 Top-K chunks
↓
基于检索结果生成回答
↓
输出答案 + 来源引用
```

用一句话解释：

系统先把企业售前文档切分成小块，并转成向量存入 Chroma；当用户提出问题时，系统会检索最相关的文档片段，再基于这些片段生成带来源引用的回答。

它模拟了 AI Solutions Intern、AI Pre-sales Intern 或 Technical Consultant Intern 在真实工作中会遇到的问题：

* 如何理解客户问题？
* 如何从产品资料中找到依据？
* 如何生成可信、专业、可追溯的回答？

* 如何把 AI 能力嵌入真实业务流程？

因此，这个项目不是一个普通的聊天机器人 Demo，而是一个面向真实业务流程的 AI 应用项目。

## 8. 当前版本的限制

当前版本仍然有一些限制：

1. 回答生成部分主要使用 Mock LLM 或模板化生成，暂时没有接入真实 LLM API。
2. Evaluation 还比较初步，需要扩展更多测试问题。
3. 目前主要是命令行运行，还没有完整的前端界面。
4. 检索质量还没有做系统性优化，例如 reranking、chunk size 对比等。

这些限制也是后续可以升级的方向。

---

## 9. 后续升级方向

后续可以从以下方向升级：

1. 接入真实 LLM API，例如 OpenAI、Qwen 或 DeepSeek。
2. 增加 Streamlit 前端，让用户可以在网页上输入问题。
3. 增加 evaluation report，量化检索准确率和引用正确率。
4. 增加 reranking，提高检索结果质量。
5. 增加 human-in-the-loop 审核机制，适合高风险售前回答。
6. 支持上传新文档并自动更新向量库。

## 10. 面试时的一分钟介绍

我的项目是一个面向 B2B SaaS 售前场景的 RAG 知识库助手。

它解决的问题是：售前人员在回答客户关于产品、价格、部署、安全、API 和客户案例等问题时，往往需要查找很多分散资料，效率低，而且容易回答不一致。

所以我构建了一个本地 RAG 系统，先把 Markdown 格式的售前知识库切分成 chunks，再通过 embedding 转成向量，并存入 Chroma 向量数据库。当用户提出问题时，系统会先检索最相关的文档片段，再基于这些片段生成带来源引用的回答。

这个项目的重点不是做一个普通聊天机器人，而是模拟真实 B2B 售前知识管理场景，强调 source grounding、可追溯回答和降低幻觉风险。
